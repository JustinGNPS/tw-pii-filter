# 載體二：AI coding agent 防護 —— 設計說明

> 負責人：B　｜　程式碼：`proxy/`
>
> 這份文件只寫**決定與理由**，不寫操作步驟（操作見 `proxy/README.md`）。
> 目的是讓組員、未來維護者與評審看得懂「為什麼這樣做」，而不是「怎麼跑起來」。

---

## 一、這個載體要解決什麼

偵測核心（A 的規則層 + D 的語意層）是**純函式** —— 給它一段文字，它告訴你
哪幾個字元是個資。它不會攔截、不會連網、不會修改任何東西。

**認得出來，不等於防得住。** 使用者用 AI coding agent（Aider、Cline…）寫程式時，
agent 會把整個檔案送去雲端 LLM，個資照樣外洩 —— 偵測核心放在那裡，沒有人會呼叫它。

載體二負責把偵測核心接到真實的資料外洩路徑上：

> **A 和 D 負責「認得出來」，B 負責「真的攔得下來、換得掉、還原得回去」。**

`proxy/` 底下沒有任何 AI 或模型，只有網路協定處理與字串操作。

---

## 二、關鍵架構決定：攔截點在 LLM API 層

### 為什麼不是攔 agent 讀檔

最直覺的做法是攔在「agent 讀取檔案」的那一步。**做不到** —— 目標的六款 agent
讀檔都走各自內建的功能，那段程式碼在 agent 內部，外部插不進去。

### 所以攔在它非經過不可的地方

agent 要把內容送給雲端 LLM，就一定得走網路，而網路位址是可以改的。

```
① 使用者下指令
       ↓
② agent 自己讀檔                    ← 攔不到，也不需要攔
       ↓
③ agent 把內容打包成 API 請求
       ↓
④ 送出 ─────────────→ proxy         ← 唯一可靠的攔截點
       ↓
⑤ 遮蔽 → 雲端 LLM → 還原
       ↓
⑥ 回給 agent
       ↓
⑦ agent 自己把修改寫回檔案           ← 攔不到，也不需要攔
```

### 這個決定的副作用（是優點）

proxy **只看得到 agent 決定要送出去的東西**。agent 讀了但沒送出去的檔案，
proxy 看不到 —— 而那些本來就沒有外洩風險。

**職責範圍剛好等於風險範圍**：只要離開這台機器的，都經過 proxy。

## 三、資料流

```
agent 送出：  {"messages":[{"content":"客戶 A123456789 電話 0912345678"}]}
                    ↓
      ① 從 payload 挖出該掃的欄位（detector.extract_texts）
      ② 呼叫 core.rules.detect_all() 取得 spans
      ③ 對照表配佔位符，從後往前替換（masker）
                    ↓
上游收到：    {"messages":[{"content":"客戶 [TW_ID_1] 電話 [TW_PHONE_M_1]"}]}
                    ↓
              雲端 LLM 全程只看到佔位符
                    ↓
上游回覆：    "...把 [TW_ID_1] 改成常數..."
                    ↓
      ④ 查對照表換回真值（restorer，含 SSE 串流重組）
                    ↓
agent 收到：  "...把 A123456789 改成常數..."   ← 與未經過濾時一致
```

---

## 四、設計決定與理由

### 1. 遮蔽與還原必須同時上線，不可分兩階段交付

**這是實測結論，不是設計偏好。**

第一版（只警告不遮蔽）驗證時，暫時讓 proxy 真的遮蔽後轉發，結果：

| 測試 | 結果 |
|---|---|
| 叫 Aider 修改**不含**個資的那一行 | 正常 |
| 叫 Aider 修改**含有**個資的那一行 | **失敗**：`SEARCH/REPLACE block failed to match!` |

原因：Aider 用 diff edit format，請 LLM 產生「找這段 → 換成這段」。LLM 依
**已遮蔽**的內容產生 SEARCH 區塊，Aider 拿去比對硬碟上**未遮蔽**的檔案，對不上。

→ 存在「只遮蔽、還原之後再說」的中間版本是壞的。這也反過來證明還原機制
不是加分項，而是讓遮蔽能用的前提。

### 2. 對照表只存記憶體，不落地

真實個資**不寫入任何檔案**，proxy 行程結束即消失。

不產生的東西不可能外洩，因此也不需要處理加密、存取權限與刪除時機 ——
把一整類風險從根本上移除，而不是想辦法管理它。

代價：proxy 重開後先前的對照就沒了。實務上不是問題 —— proxy 重開時
agent 的對話也已中斷，本來就要重來。

### 3. 佔位符號碼由 proxy 自己發，不採用 `detect_all` 的 `replacement` 序號

`detect_all()` 每次呼叫都從 1 重新編號，而 **agent 每次請求都會重送整段對話歷史**：

```
第 1 次請求： A123456789 -> [TW_ID_1]
第 2 次請求： A123456789 -> [TW_ID_2]      同一人換了號碼
              F131104093 -> [TW_ID_1]      1 號被別人拿去用
```

還原時就會**把兩個人的個資對調** —— 比洩漏更嚴重的錯誤。

因此 proxy 自己維護對照表：**一個真值第一次出現時配一個號碼，之後永遠是那個號碼**。
`type` 與座標仍完全採用 `detect_all()` 的結果。

> A 已於 `interface.md` 加入「仲裁後重新編號、不跳號」的保證。那解決了**單次
> 呼叫內**的連續性，但跨請求的穩定性仍需由 proxy 這一側維護，因此本決定不變。

> **後續驗證（回應 C 在 PR #4 提的作用域問題）**：曾經考慮「一個請求一張表」
> 是否可行（agent 拿到的回覆已還原成真值，下次重送的歷史理論上不需要舊的
> 對照記錄）。用 `tests/test_mapping_table_scope.py` 實測證明**不成立**：
> 只要新實體在文字裡排在舊實體前面，新表從 1 開始配號會讓舊實體的號碼被
> 搶走，跟這裡描述的「1 號被別人拿去用」是同一類問題，只是觸發原因從
> 「A 重新編號」換成「表重開一次」。**結論維持整個行程共用一張表**，
> 這不是偷懶沒做，是驗證過的決定。C 的「單一對話、12 小時過期」是對的
> 設計，只是兩個載體回答的是不同問題（agent 長工作階段的一致性需求，
> vs. 使用者零散貼上不該累積可追蹤識別子），不需要對齊。

### 4. 從後往前替換

替換會改變文字長度。`A123456789`（10 字元）換成 `[TW_ID_1]`（9 字元）後，
整段文字短了 1 個字元，**後面所有 span 的座標都會偏掉**。

由座標大的往小的替換，每次替換只影響已處理完的部分。

### 5. 查不到的佔位符一律原樣保留，絕不猜測

LLM 可能自己編出從未發出過的佔位符（幻覺）。猜測等同於**憑空捏造一筆個資
塞進使用者的檔案** —— 比洩漏更糟。查不到就原樣放行並記錄。

### 6. 偵測失敗不能弄壞 agent

遮蔽流程包在 try/except 裡，失敗時原樣轉發。代價是該次請求不受保護，
因此會以 ERROR 等級留下紀錄。

理由：proxy 的第一要務是不要弄壞 agent。**一個會讓 agent 壞掉的防護工具，
使用者會直接移除它，防護效果歸零。**

### 7. log 只記型別與筆數，絕不記原始內容

log 檔本身就是個資外洩管道。有專門的測試守這條規則。

### 8. 偵測結果快取

agent 每次請求都重送整段對話歷史，同一份檔案內容會被重複掃十幾次，結果完全相同。
偵測是純函式，因此可安全快取。key 為文字的 SHA-256 指紋（不存原文），
採 LRU 並設大小上限。

模擬 8 輪對話（共 36 個欄位，其中只有 8 個是新的，命中率 78%）：

| 情境 | 無快取 | 有快取 | 省下 |
|---|---|---|---|
| 純規則層 | 59.9 ms | 18.0 ms | 70% |
| 假設語意層每次推論 200 ms | 7261 ms | 1619 ms | 78% |

第二行是重點：語意層接進來後，**沒有快取的話光偵測就要等 7 秒**。

### 9. 型別代碼一律正規化成大寫

`interface.md` 定義的型別代碼是大寫（`TW_ID`、`EMAIL`…），但語意層（D 的 NER）
實測時原生輸出過小寫的 `name` / `address` / `position`。若原樣拿去發佔位符，
會產生 `[name_1]`，而還原用的 `TOKEN_PATTERN` 只認大寫 —— **遮蔽成功、還原
靜默失效**，佔位符會被留在使用者的檔案裡（不拋錯、不報警告，很難查）。

`core/redact/mapping.normalize_type()` 在**入口**（`token_for()`）一律先把型別代碼
轉成 `[A-Z][A-Z_]*` 的形式。只做格式正規化，不做語意改名 —— 不會把 `name`
自作主張改成 `PERSON`，型別代碼叫什麼是 `interface.md` 的決定，不是 proxy 的。

**沒有選擇放寬正則去接受小寫**：`[abc_1]` 這種寫法在一般程式碼裡很常見，
放寬會讓還原去動到不該動的內容。**收緊入口，比放寬出口安全。**

順帶解掉一個撞號風險：`name` 與 `NAME` 若被當成兩個型別，兩邊都從 1 號開始
發號碼，會產生兩個 `[NAME_1]` 指向不同的人，還原時把兩人的個資對調。

> D 後來在 `core/ner/detector.py` 也把型別代碼在**源頭**轉大寫（`entity_group.upper()`），
> 這件事因此變成**雙重防線**而非唯一防線 —— 上游修好了，下游的防禦仍然留著，
> 不會互相衝突，也不需要因為上游修好就撤掉。

### 10. 語意層接線：預設關閉，需要時才啟用

`proxy/detector.py` 的 `detect()` 已接上 `core.ner.detect_ner()`，結果當
`extra_spans` 一起送進 `detect_all(text, extra_spans=...)`。規則層與語意層
**各自獨立掃描同一段文字**，只在 Layer 4 合併、仲裁重疊 —— 規則層的 8 種
型別不會被語意層重新判斷，反之亦然。

新增 `PII_ENABLE_NER` 環境變數，**預設關閉**：

- 語意層單次推論（CPU）約 **2412 ms**，是規則層（2〜4 ms）的六百多倍，且是
  同步阻塞呼叫；開著會讓每個請求都平白付這筆延遲。**這個數字修正過一次**：
  最初測到的 742 ms 其實是「沒掃完整份文字」測出來的假快——D 後來發現
  `bert-base-chinese` 有 512 token 上限，超過的內容被 pipeline 靜默截斷
  （症狀正是 FN 集中在檔案後段），修好截斷後重新量測才是 2412 ms 這個
  真數字（見 PR #15）。**742 ms 這個數字已作廢**，本文件與 `proxy/README.md`
  先前引用過，已一併更新
- `core.ner.detector` 內部會 `import torch` / `transformers`，屬於 GB 等級的
  重量級套件；關閉時 proxy 完全不 import 這個模組，不強迫沒有語意層需求的人安裝

開啟語意層後，`_mask_request`（原本是同步函式，直接在 async 的請求處理裡
被呼叫）改用 `asyncio.to_thread` 丟到背景執行緒，避免這筆同步阻塞卡住
同一個 proxy 行程裡其他請求排隊等它。規則層單獨運作時這筆改動感覺不出差別
（本來就快），但語意層一開就是必要的——2412 ms 比早先以為的 742 ms 更嚴重，
這個決定因此更加正確。

用真實模型（非 mock）跑過一次端到端驗證：規則層與語意層的結果正確合併，
`position`（職稱）依約定不遮蔽，`NAME`/`ADDRESS` 正確遮蔽並完整還原，
即使語意層當時仍輸出小寫型別，也被決定 9 的正規化正確擋下。

### 11. 對照表清除策略：閒置逾時清除（已決定，未實作）

呼應決定 2「對照表只存記憶體」——不落地解決了「外洩」，沒解決「駐留太久」。
專題報告 §7.2 把對照表列為攻擊面之一，若這條在送件時仍是「未決」，評審大概
會問。C 在 PR #12 review 提醒過這件事，**這裡先把決定寫下來，不代表這次就要
把 `clear()` 接上去**（`MappingTable.clear()` 已經備妥，等有餘力再接線）。

**決定**：`MappingTable` 閒置超過一段時間（預設 30 分鐘，可用環境變數調整）
就整張清空，不採條目數上限，也不做逐筆過期。

**為什麼是閒置逾時，不是條目數上限或逐筆過期**：

- proxy 沒有「對話」的概念——跟 C 的擴充不同，擴充有對話網址可以當 key。
  proxy 看到的只是一連串 HTTP 請求，agent 有沒有開新對話、使用者是不是已經
  離開，proxy 判斷不出來，唯一能觀察到的訊號是「有沒有新請求進來」
- 逐筆過期（每個真值各自算自己的存活時間）需要額外的資料結構與時間戳記
  維護，換不到明顯的好處——同一個 agent 工作階段裡的個資通常一起活、一起死
- 條目數上限（像 `DetectionCache` 的 LRU）保護的是「單次工作階段內不斷
  成長」，閒置逾時保護的是「工作階段結束後仍駐留」，兩者是不同風險、不衝突，
  但這次先解決 C 提的那個問題（明文個資駐留時間 = proxy 開機時間）。條目數
  上限留到真的觀察到單一工作階段膨脹到有感的程度再加，避免預先設計用不到
  的機制

**為什麼清空是安全的，不會弄壞正在進行的對話**：AI 的回覆在離開 proxy 前
就已經把佔位符還原成真值（見決定 1、決定 4），因此 agent 端保存的對話歷史
從頭到尾都是真值，不曾包含佔位符。閒置清空後，下一個請求會用一張全新的表
重新配號——不影響任何正確性，唯一的代價是佔位符數字重新從 1 開始（demo 時
使用者可能覺得數字「重置」了，跟遮蔽/還原功能本身無關）。

**觸發方式（設計，尚未實作）**：不開額外的背景執行緒或計時器輪詢，比照專案
目前的風格（`_mask_request` 也是同步計算，沒有額外的背景工作）——在
`MappingTable` 記錄最後一次被存取的時間戳，`token_for()` / `restore_text()`
被呼叫時先檢查距上次存取是否超過門檻，超過就在處理這次請求前自己
`clear()`。不需要額外執行緒，成本只有一次時間比較。

### 12. 組合風險（Layer 3）：只提示，不遮蔽；用遮蔽後的內容評分

D 的 `core/risk/combination_risk.py`（規格：A 的 `docs/layer3_spec.md`）算的是
「明碼個資全部遮掉之後，剩下的內容還能不能指認到特定個人」。B 這一側負責把它
接上真實流量，接線邏輯在 `proxy/risk.py`。

**這一層要處理的洩漏，遮蔽機制本質上擋不住**。報告第 4.3 節引用的 llm-redactor
實測：把明顯的 PII 字串都遮掉之後，「隱含身分」洩漏率仍達 95%。典型例子是
「35 歲、女性、新竹市東區、資深後端工程師」——沒有任何一個欄位是個資，組合
起來卻只對應到極少數人（Sweeney 2000：性別＋郵遞區號＋生日三個準識別子即可
重新識別 87% 的美國人口）。

**決定 A：只印 log，不動 payload，也不阻擋請求。**

不是實作偷懶，是這個問題沒有自動解。要壓下組合風險就得連年齡、性別、職稱一起
遮，但那正是 agent 讀懂上下文所需的資訊——全遮掉之後送出去的是
`這位 [AGE_1] 的 [GENDER_1]，是我們公司的 [POSITION_1]`，AI 什麼忙都幫不上。
遮到什麼程度值得，取決於使用者當下在做什麼任務，proxy 判斷不了。`layer3_spec.md`
因此把定位訂成「偵測並警示，讓使用者自己判斷」，本實作照這個定位走。

同樣的理由，這個評分**不進 `/healthz`**：它是逐請求的內容屬性，不是服務健康
狀態，混進健康檢查只會讓監控語意變模糊。

**決定 B：餵給評分器的是「遮蔽後的文字 ＋ 沒被遮掉的 spans」，不是原文。**

這是實作時才想清楚的一點。直覺會想用原文評分（資訊最完整），但那會**虛報**：
`ADDRESS` 預設會被遮掉，遮完之後 AI 只看得到 `[ADDRESS_1]`，地址對重新識別
已經沒有貢獻，卻仍會被計入分數。反過來 `POSITION` 預設不遮
（`config.SKIP_TYPES`）、`AGE`／`GENDER` 根本沒有任何一層在偵測——這幾類才是
真正會送出去的殘餘風險。

組合風險本來就該定義成「**遮完之後還剩下多少**」，用原文算等於在警告一個已經
被自己擋掉的洩漏。實測可以看出差別：上面那個例子若用原文評分是 1.00（滿分），
用遮蔽後的內容評分是 0.70——少掉的 0.30 正是已經被遮蔽處理掉的 `ADDRESS`。

**原作者確認（2026-08-12，PR #25）**：D 確認這個用法**正確且一致，不是誤用**——
`compute_combination_risk(text, spans)` 評估的是「你給的這份 `text` 實際看得到
什麼」，不是「這段內容理論上曾經含有什麼」，所以它內部才會直接對 `text` 做
AGE／GENDER 正則掃描，而不是只信任 `spans`。這個 text/spans 配對契約已經寫進
函式 docstring，明確列出兩種合法用法（原文＋完整 spans／遮蔽後＋殘餘 spans）
與一種錯誤用法（`text` 用遮蔽後、`spans` 卻用原文的完整偵測結果，會虛報）。

**這個契約也解釋了 `proxy/risk.py::_assess_risk()` 的一個實作決定**：它沒有
沿用 `scan_payload()` 的結果，而是重走一次 `detector.extract_texts()`。因為
`scan_payload()` 只回傳「有偵測到 span 的欄位」，但既然評分器是對文字本身做
掃描，「有沒有 span」就不是該不該送去評分的判準——一個像「這位 35 歲的女性想
諮詢」的欄位可能**一個 span 都沒有卻仍有風險**，只看有 span 的欄位會整段漏掉。

**那 0.30 的差距是遮蔽有效性的量化證據，不是兩邊算錯。** D 的說法值得原樣記
下來：權重表照 Sweeney (2000) 給 `ADDRESS` 最高權重之一，遮蔽後分數大幅下降，
正好同時證明「這個型別的識別力確實很強」與「遮蔽措施確實有效」——**如果遮不遮
幾乎沒差，那才代表權重設計有問題**。

**決定 C：一個請求最多印一行，取分數最高的欄位。**

agent 每一輪都重送整段對話歷史，同一則高風險訊息會在每輪重新出現。逐欄位印會
讓 log 被同一段內容洗版，真正該注意的那行反而被淹沒。

**決定 D：門檻沿用 D 的 `is_warning_worthy()`（0.6），不在 proxy 端另訂一套。**

門檻值有它的依據（見上述 Sweeney 的三個準識別子），在 proxy 這一側複製一份
只會讓兩邊哪天悄悄分歧。

**決定 E：泛化建議照原樣印，包含從內容抓到的年齡數字。**

警示訊息裡會出現「「35歲」建議泛化為「35-39歲」」這種句子。這違反了決定 7
（log 只記型別與筆數）的字面規定，因此明確記錄理由：log 只寫在本機、不外傳；
年齡不在任何遮蔽型別裡，本來就會原樣送給雲端 AI，印在本機 log 不構成額外
暴露；而泛化建議不講具體數字就失去可操作性。**除了建議句以外，警示訊息不含
任何原文片段**，被遮蔽掉的真值一個字都不會出現。

**成本：+0.10 ms／請求**（10 輪對話歷史、每則含假客戶清單的模擬 payload，
50 次平均）。評分只有正則與集合運算，沒有偵測成本。這相對遮蔽本身是 +44%
（遮蔽有快取，本來就只有 0.22 ms），但相對整個請求的往返時間（上游約
2000 ms）是 0.005%——兩個比例都列出來，避免只講其中一個造成誤導。

**已知限制：語意層關閉時，這個警示實質上不會觸發。**

規則層那 8 個型別（`TW_ID`／`TW_TAX`／`EMAIL`…）沒有一個是準識別子——它們是
直接識別碼，本來就會被遮掉。準識別子裡 `ADDRESS`／`POSITION`／`COMPANY` 只有
語意層抓得到，`AGE`／`GENDER` 則是 D 的模組自己用正則抓。因此
`PII_ENABLE_NER=0`（預設）時，可貢獻分數的只剩 `AGE` + `GENDER` = 0.50，
永遠碰不到 0.6 的門檻。

這不是 bug，是兩層能力範圍的必然結果，但**demo 時要記得開 `PII_ENABLE_NER=1`
才看得到 Layer 3 的效果**。`tests/test_risk.py` 有一個測試專門釘住這個行為，
避免日後被誤判成壞掉。

### 13. 語意層改用型別白名單，`COMPANY` 預設不遮

> 決定 12（Layer 3 組合風險提示）在 PR #25，尚未合併，所以本文件目前從 11
> 直接跳到 13。編號已保留，兩條分支都進 `main` 之後就會連續。

**問題是怎麼被發現的**：08-14 用真 Claude Code CLI 跑端到端測試（開語意層），
第一個請求只送了 `hi`，log 卻印出：

```
[WARNING] 已遮蔽（Claude Code）：偵測到 8 筆敏感資訊（GAME x7、ORGANIZATION x1）
```

使用者內容只有兩個字元，所以這 8 筆全部來自 Claude Code 自己的 system prompt。

**查證**：`python core/ner/get_model_labels.py`（直接讀模型 config 的
`id2label`，不是靠測試句子歸納）顯示 `gyr66/bert-base-chinese-finetuned-ner`
共有 **14 種**標籤，不是我們一直以為的 4 種：

```
QQ, address, book, company, email, game, government,
mobile, movie, name, organization, position, scene, vx
```

用 08-11 capture 的真實請求（36,428 字元）確認實際被遮掉的內容：

```
GAME         x6   'here'  'ollama'  '—'  'MEMORY'  '`'  'Environment\nYou'
ORGANIZATION x2   'mistral'  '`'
```

**一個反引號被判成 `GAME`、遮成佔位符送給上游。**

**這是功能損害，不是隱私問題** —— 那些本來就不是個資。損害有兩層：agent 的
系統提示被挖洞、行為可能受影響；log 的「偵測到 N 筆」被灌水，使用者無從得知
其中幾筆是真的（實測那輪「45 筆」裡有 8 筆是雜訊）。

**根因**：這是**通用領域**中文 NER 模型，而 agent 送來的大量是**英文技術
文字**，落在訓練分布之外。

#### 決定 A：語意層改用白名單，不是擴充黑名單

新增 `PII_NER_ALLOW_TYPES`（預設 `NAME,ADDRESS,POSITION,COMPANY`），白名單外
的語意層 span 在**送進 `detect_all(extra_spans=...)` 之前**就丟棄。

**為什麼是白名單**：黑名單要求我們預先知道模型的所有標籤 —— 而這個專案有
11 天都以為只有 4 種，直到 08-14 才去核對模型本身。白名單在日後換模型、模型
改標籤集時都不會被新標籤偷襲。**這個決定的價值不在於今天擋掉哪 10 種型別，
而在於把「預設信任」改成「預設不信任」。**

**為什麼丟在 `detect_all()` 上游**：丟掉的 span 從一開始就不存在，因此不參與
Layer 4 仲裁（雜訊不會有機會擠掉真正的規則層結果）、不進 log 筆數、不進
Layer 3 分數。這三件事都是「當作沒偵測到」的應有語意。

#### 決定 B：`COMPANY` 預設不遮，但**留在白名單內**

回應 D 在 `core/ner/detector.py:24-25` 從 08-03 掛到現在的提問（「company
是否算目標 PII 屬政策問題，可考慮預設不遮蔽」）。公司／店名不是個人識別資料，
遮掉會讓 agent 讀不懂程式碼（類別名稱、套件名稱常含公司名）。加進
`DEFAULT_SKIP_TYPES`。

**關鍵在於「不遮」與「不採信」必須分開**：`COMPANY` 進 `SKIP_TYPES`（不遮）
但**留在 `NER_ALLOW_TYPES` 裡**（採信）。因為 AI 真的看得到公司名，它對重新
識別的貢獻是真實的，權重 0.15 必須照算進 Layer 3。若圖省事把它排除在白名單
外，風險分數會**漏報** —— 那正是決定 12 極力避免的錯（只是方向相反：決定 12
防的是把已遮蔽項目算進去的**虛報**）。

`POSITION` 一直都是這個模式，這次只是把它寫清楚並讓 `COMPANY` 跟上。

| | `NER_ALLOW_TYPES`（白名單） | `SKIP_TYPES`（跳過清單） |
|---|---|---|
| 意思 | 型別根本不可信，當作沒偵測到 | 偵測是對的，政策上不遮 |
| 進 Layer 4 仲裁 | ❌ | ✅ |
| 計入 log 筆數 | ❌ | ✅ |
| 計入組合風險分數 | ❌ | ✅ |

#### 效果與**沒有**解決的部分

同一份實測資料，`GAME x6` 與 `ORGANIZATION x2` 全部消失，真個資完全不受影響
（三個姓名、三個地址仍是 1.00 信心，規則層的身分證／手機不受影響）。

**但白名單擋不掉「白名單型別內部」的誤判**：同一份資料裡英文字碎片 `'lly'`
被判成 `NAME`、信心 0.99，這筆仍然會被遮。9 筆雜訊降到 1 筆，沒有根治。
根因是拿中文通用模型掃英文技術文字，要真正解決得換模型或加語言判斷，
兩者都超出載體端的範圍 —— 這點**必須誠實寫在報告裡**，不能只講降了 8 筆。

## 五、已知限制與取捨

### 1. 關聯性洩漏（刻意的取捨）

同一真值永遠對到同一佔位符，因此雲端 LLM 可以推論「這兩處是同一個人」：

```
檔案 A：  客戶 [TW_ID_1] 的訂單
檔案 B：  [TW_ID_1] 的退款申請
```

真實身分 LLM 無從得知，但關聯性洩漏了。

**不能靠「每次換不同佔位符」解決** —— 那會讓 agent 的 diff 比對失敗（見決定 1）。
一致性是功能上的必要條件，因此這是有意識接受的取捨，而非疏漏。

### 2. Cursor 攔不到——這其實是一整類問題，不是單一工具的個案

Cursor 走自家後端，不提供指定 base URL 的方式，**誠實列為不支援**。

**這個限制該推廣成一個判準，不是只記 Cursor 一個特例**：proxy 能不能防護
某個 agent，關鍵不在工具叫什麼名字，而在於**它有沒有一個「自訂 API 位址
（Base URL / Endpoint）」的欄位可以填**。

- **能填自訂位址（BYOK，bring your own key）**：Aider、OpenCode、Continue、
  Cline 這四款已實測都屬於這類——使用者拿一把上游供應商的金鑰（OpenAI、
  Anthropic，或任何 OpenAI 相容服務），填進 agent 的自訂位址欄位，
  proxy 才插得進去。
- **只能登入帳號、走廠商代管後端（例如 Cursor、Cline 的 ClinePass／
  OpenCode 自家代管付費方案）**：沒有位址欄位可以改，流量直接進廠商
  自己封閉的伺服器，**proxy 完全無從介入，不管那款工具原本支不支援
  自訂位址、也不管是不是付費方案**。

換句話說：**「使用者是否已經在使用某個 agent 的代管付費方案」直接決定
這個 agent 能不能被本專案防護**——如果是代管方案，即使 agent 本身在
BYOK 模式下可以被攔，登入代管方案的那個使用情境依然攔不到。這不是
臨時發現的邊角案例，是**架構層級的硬限制**：proxy 攔截的前提是「流量
的目的地位址可以被使用者自己改」，代管服務的整個賣點恰好就是不讓你改。

**金鑰從哪裡來、算誰的額度**：BYOK 模式下，proxy 只是把金鑰的存放位置
從「每個 agent 各自的設定」集中到「proxy 的 `.env`」，額度算的仍然是
**該金鑰持有者**的帳——proxy 開發者（B）不銷售、不提供 token，`.env`
裡要放誰的金鑰、算誰的帳，由**架設這台 proxy 的人**決定。可能是個人
使用者放自己的 OpenAI／Anthropic 金鑰（額度算自己的），也可能是團隊／
組織集中放一把共用金鑰讓底下所有人共用（例如本專題示範用的長庚 AIR
測試帳號，就是這種集中管理的模式）——兩種都合理，差別只在於「誰負責
管理那把金鑰」，跟 proxy 本身的防護能力無關。

### 3. 效能數字分規則層／語意層兩套，不能混著講

`proxy/README.md` 記載的「額外成本約 5 ms、占上游往返 0.25%」是**純規則層**
的數字，且維持不變 —— 規則層預設永遠開，這是本專題相對 Presidio / GLiNER
等工具的核心優勢（確定性偵測、有 checksum、幾乎不漏）。

語意層（`PII_ENABLE_NER=1`）接入後，單次推論（CPU）約 **2412 ms**，是規則層
的六百多倍，且預設**關閉**（見決定 10）。兩層數字性質不同，評審若問「會不會
漏」時，這正是規則層（確定性、recall 接近 100%）與語意層（機率性、
D 修好 512 token 截斷問題後重新實測 **recall 97.6%**，比修之前的 92.7% 更好，
因為之前漏的那些有一部分正是被靜默截斷、根本沒進模型的內容）該分開講的
原因 —— 混在一起講反而站不住腳。

#### 那個 2412 ms 是「單次短文本」的數字，實際 agent 場景要換個算法

`2412 ms` 是 D 用一段短測試文字量出來的。在 agent 場景這個數字會誤導：D 為了
修 512 token 靜默截斷，把長文字改成分段處理（400 字元一段、重疊 50 字元），
因此**推論成本跟文字長度成正比，不是固定值**。而 agent 送出的 payload 動輒
含整份檔案內容。

用 08-11 capture 下來的**真實 Claude Code 請求**（155,608 字元的 payload，
8 個待掃描欄位、合計 36,428 字元）實測，模型已預熱：

| 欄位 | 長度 | 推論耗時 |
|---|---|---|
| Claude Code 的 system prompt | 27,629 字元 | 9,926 ms |
| `<system-reminder>` agent 類型說明 | 7,173 字元 | 2,781 ms |
| **`Read` 讀到的檔案內容（真正的使用者內容）** | 1,089 字元 | 527 ms |
| 其餘 5 個小欄位 | 各 42〜306 字元 | 合計 247 ms |

**約 0.36 ms／字元**（小欄位有固定開銷，平均起來約 0.6 ms／字元）。

**95% 的成本花在 Claude Code 自己的樣板文字上** —— system prompt 與
`<system-reminder>` 合計 34,802 字元，是 Anthropic 寫死的 agent 指令，不可能
含使用者個資，卻占掉 12.7 秒。

#### 但這是一次性成本，決定 8（偵測快取）正是為此存在

同一個 proxy 行程連續處理多輪對話（第 2 輪起 agent 重送整段歷史 + 新訊息）：

| 輪次 | 耗時 | 快取命中率 |
|---|---|---|
| 第 1 輪（全新 session） | **13,394 ms** | 0% |
| 第 2 輪（同 system prompt + 1 則新訊息） | **46 ms** | 47% |
| 第 3 輪（再多 1 則） | **32 ms** | 63% |
| 第 4 輪（agent 讀到新檔案，約 2000 字元） | **1,217 ms** | 71% |

**語意層只對「這個行程沒看過的內容」收費**。system prompt 每輪都出現、每輪
都命中快取，13 秒只付一次；之後每輪的成本正比於**新增內容**的長度。

這是決定 8（偵測快取）在 agent 場景的真正價值 —— 沒有它，每一輪都要重付
13 秒，語意層在這個載體上根本不可用。07-29 做那個決定時的理由是「agent 每次
重送整段歷史，同一份檔案被重複掃十幾次」，當時只有規則層、省下的是幾毫秒；
語意層接上後才看得出這個決定實際上是**讓語意層可用的前提**。

**實務結論（demo 前一定要知道）**：開 `PII_ENABLE_NER=1` 時，**proxy 啟動後
的第一個請求會等約 13 秒**，agent 看起來像卡住。demo 前先隨便送一個請求把
快取暖起來，之後就順了。模型載入本身（約 3,951 ms）已經由 `lifespan()` 在
啟動時預熱掉，不算在這 13 秒裡。

#### ⚠️ 不要「最佳化」成跳過 `system` 欄位

看到「95% 成本花在 agent 的樣板文字上」，很自然會想到：那就別掃 `system`
不就好了？**不可以。**

`system` 陣列裡確實大部分是 Anthropic 寫死的指令，但**不是全部**。同一份
capture 裡就有一個 306 字元的欄位長這樣：

```
<system-reminder>
As you answer the user's questions, you can use the following context:
# claudeMd ...
```

這是 Claude Code 把**專案的 `CLAUDE.md` 與使用者的記憶檔內容注入 system
prompt** —— 那是不折不扣的使用者內容，可能含個資。08-11 開發協定轉換層時也
發現過 `messages[].role == "system"` 的中途系統訊息同樣會夾帶使用者內容。

**判準是「這段文字從哪來」，不是「它在哪個欄位」**，而 proxy 沒有可靠的方法
從 payload 區分哪一段是 Anthropic 寫的、哪一段是使用者的。掃描範圍寧可過寬
（多花時間）也不能過窄（漏掉個資）—— 而且成本問題已經被快取解決了，這個
最佳化省不到真正的錢，只會換來漏掃的風險。

### 4. 為什麼不用 MITM／網路層攔截去救「代管帳號」

限制 2 的結論是「沒有自訂位址欄位就攔不到」。很自然的下一個問題是：**那能不能
不靠 agent 配合，直接在網路層攔？** 例如架一個系統層級的中間人代理，把所有
往 `api.cursor.sh` 的流量攔下來改寫。

**結論：不做。** 這不是能力不足或時間不夠，是四個獨立的理由各自都足以否決，
其中兩個是死結。

**① 憑證釘選（certificate pinning）是技術死結。**
一般的 HTTPS 攔截靠「在使用者機器裝一張自簽根憑證，讓 app 相信中間人」。但
只要 app 把預期的憑證指紋寫死在程式碼裡（釘選），這招就完全無效 —— app 會
發現憑證不對、直接斷線。要繞過就得改 app 本身（patch 二進位檔、hook
系統呼叫），那已經不是「寫一個 proxy」的範疇。

**② 就算繞過了，還要逐一逆向每款 app 的私有協定。**
代管服務不需要對外相容，格式想怎麼定就怎麼定，而且**隨版本更新隨時會變**。
本專案能支援六款 agent，靠的正是它們都講 OpenAI／Anthropic 這兩種**公開且
穩定**的協定；私有協定沒有這個性質，等於每款 agent、每次改版都要重做一次
逆向。這不是一次性成本，是永久的維護負擔。

**③ 幾乎必然違反服務條款。** 主流 AI 服務的條款普遍禁止逆向工程與規避技術
限制。一個以「保護使用者隱私」為訴求的工具，靠違約手段運作，說服力會自相
矛盾 —— 而且會讓採用它的組織承擔法律風險。

**④ 最根本的：它要求使用者降低自己系統的安全等級。**
MITM 必須在使用者機器安裝一張根憑證。那張憑證一旦存在，**任何拿到對應私鑰
的人都能冒充任何網站**，包括網路銀行。也就是說，為了防止個資流向 AI，得先
在系統上開一個比原問題更大的洞。**一個隱私保護工具不該要求使用者為它承擔
這種風險**，這個理由跟前三個不同 —— 就算前三個技術上全都解決了，這一個
依然成立。

**所以限制 2 是誠實的架構邊界，不是待辦事項。** 「有自訂位址欄位才攔得到」
這句話同時是本專案的**適用範圍聲明**，也是它**不去做那些事**的理由。

### 5. 檔案級遮蔽：另一條路，取捨不同（沒有採用，但值得記錄）

`work_B.md` 最早提過另一個構想：**不攔網路層，改在檔案層做** —— 使用者在
讓 agent 讀專案之前先跑一次遮蔽（把檔案裡的個資換成佔位符），等 agent 改完
之後再跑一次還原。

**它唯一勝過 proxy 的地方，正好是 proxy 最大的限制**：它完全不管流量走去
哪裡，所以**連 Cursor 這種代管帳號也保護得到**（限制 2 那一整類問題直接
繞開），而且不需要憑證、不需要逆向、不違反任何條款 —— 限制 4 那四個否決
理由一個都不適用。

**但它付出的代價是本專案的核心體驗：**

| | LLM API Proxy（本專案採用） | 檔案級遮蔽 |
|---|---|---|
| 使用者要做什麼 | 設一次 base URL，之後**完全無感** | 每次都要手動跑遮蔽／還原兩個步驟 |
| 代管帳號（Cursor…） | 攔不到 | **保護得到** |
| 使用者在對話畫面看到的 | **真值**（proxy 還原後才送到眼前） | **佔位符**（檔案本身就是遮蔽過的） |
| 保護範圍 | 所有經過 API 的內容，含使用者臨時打的字 | 只有檔案內容；使用者在對話框裡打的個資完全沒被保護 |
| 還原時機 | 自動、逐次回覆 | 使用者自己決定，忘了就是一堆佔位符留在專案裡 |

最後兩列是關鍵。**「使用者在對話畫面看到佔位符」不只是體驗差** —— agent 跟
使用者討論程式碼時滿螢幕都是 `[TW_ID_1]`，人自己也會看不懂自己的資料。而
**「對話框裡打的字完全沒保護」**是更嚴重的缺口：實務上使用者很常直接把一段
含個資的錯誤訊息貼進對話，檔案級遮蔽對這條路徑完全無能為力，而 proxy 天然
涵蓋（它攔的是 API 請求，不管內容是從檔案來的還是使用者打的）。

**選擇 proxy 的理由**：本專案主張的是「**在本地完成處理、對使用者無感**」
（見第一節）。檔案級遮蔽把處理成本轉嫁給使用者，而且保護範圍更小 —— 它換到
的「支援代管帳號」很有價值，但不足以彌補這兩點。

**兩者不衝突，可以並存。** 如果之後真的要支援 Cursor 這類代管 agent，檔案級
遮蔽是**唯一合法的路**（限制 4 已經排除了 MITM），屆時可以當成 proxy 的補充
模式提供，而不是取代它。這也呼應 C 的瀏覽器擴充 —— 三個載體攔的是三個不同
的位置（API 流量／檔案／瀏覽器貼上），覆蓋範圍互補。

### 6. agent 讀檔的編碼：中文可能在到達 proxy 之前就已經損毀

**這條限制的特別之處是：出事的位置在 proxy 上游，我們看不到、也補不了。**

2026-08-22 用真 Codex 實測時發現，agent 讀取專案檔案送上來的內容，中文全是亂碼：

```
原始檔案（UTF-8）
{"name": "林秉軒", "address": "台北市中山區民生東路二段141號"}

proxy 收到的
{"name": "??頠?, "address": "?啣?撣葉撅勗?瘞??梯楝鈭挾141??}
```

注意那些 `?` —— 不是被重新映射的字，是**編碼時對應不到直接被換成問號**，
位元組在讀檔那一刻就沒了。這也是為什麼「事後還原亂碼」這條路不可行
（D 另外做過逆運算實測，結論一致：cp950 能表示的組合遠少於 UTF-8，
資訊遺失不可逆）。

#### 根源不是終端機設定，是 agent 選了哪個讀檔指令

一開始的假設是主控台代碼頁，實測推翻了（同一個檔案、同一台機器）：

| 做法 | 結果 |
|---|---|
| `[Console]::OutputEncoding = [Text.Encoding]::UTF8` 之後 `type` | ❌ 仍是亂碼 |
| `chcp 65001` 之後 `type` | ❌ 仍是亂碼 |
| `Get-Content <file> -Encoding utf8`（完全不動主控台設定） | ✅ 完全正確 |

**壞在讀取端，不在輸出端**：Windows PowerShell 5.1 的 `type` / `Get-Content`
讀檔時預設用 ANSI 代碼頁（繁中環境是 cp950），檔案進到記憶體那一刻就已經解碼
錯誤 —— 前兩列就是證據，輸出編碼改了，字還是壞的，只是壞的樣子換一種。

所以真正的變因是**agent 產生了哪一條讀檔指令**，而那是模型當下的選擇，
proxy 管不到。

**08-22 demo 演練又獨立驗證了一次**：同一台機器、同一個檔案、同一個 agent，
這次模型挑的是 `rg`（而不是 `type`），送上來的中文**完全正常**。也就是說
這條限制不是「Windows 上一定會發生」，而是**擲骰子** —— 而擲骰子的是模型，
不是使用者。這也解釋了為什麼 08-14 觀察到、08-16 卻沒重現：
不同輪次的工具鏈用了不同的讀檔方式，不是隨機現象。

#### 影響範圍（要講準，不要放大）

| 層 | 影響 | 原因 |
|---|---|---|
| 規則層 | **不受影響** | 身分證、統編、手機、信箱、信用卡的目標字串都是 ASCII，亂碼動不到它們。實測同一份內容照樣遮到 6 筆（`TW_ID` x3、`TW_PHONE_M` x3） |
| 語意層（NER） | **等於失效** | 中文姓名、地址已經不成字，模型掃不到 |

因此這句話只能這樣寫：

- ❌ 「Windows 上語意層會失效」 —— 太大，站不住
- ✅ 「**當 agent 以未指定編碼的 `type` / `Get-Content` 讀取 UTF-8 檔案時**，
  送進語意層的中文已損毀，NER 等於失效；規則層因為目標都是 ASCII 而不受影響」

順帶一提，這個限制反而凸顯了規則層的穩健性：**正則與檢核碼不吃編碼問題，
通用領域 NER 模型吃。** 這與本專案的核心主張（規則層是台灣個資偵測的基礎）
是一致的。

#### 為什麼不做「亂碼偵測」

討論過用罕用字比例判斷「這段疑似編碼損毀」，決定**不做**，兩個理由：

1. **誤判正好打在保護目標上**（D 提出）：姓名與地址本來就比日常文字更容易
   出現罕見字（少見姓氏、生僻地名用字），用罕用字比例當警訊，最容易誤判的
   剛好是真正該保護的內容。沒有大量真實台灣姓名/地址語料驗證誤判率之前不該上線。
2. **訊號出現的時機太晚**：亂碼進到 proxy 時，個資已經在 agent 本機被破壞了。
   就算判得準，能做的也只有印一行警示 —— 擋不住、補不了，使用者當下能採取的
   行動是零。用一個誤判率不明的偵測器換一行無法行動的警示，不划算。

#### 對 demo 的影響

要展示**姓名／地址**遮蔽效果時，**不要走「叫 agent 讀檔」這條路徑**，
改用直接把內容貼進對話框（C 的瀏覽器擴充那條載體本來就是貼上，不受影響）。
規則層的展示（身分證、統編、手機）不受這條限制影響，兩條路徑都可以。

#### 未驗證

PowerShell 7（`pwsh`）的 `Get-Content` 預設編碼與 5.1 不同，理論上不會有這個
問題，但開發機沒有安裝 `pwsh`，**沒有實測，因此不寫進結論**。若之後驗證成立，
這條限制的範圍可以再收窄成「Windows PowerShell 5.1」。

追蹤：issue #37。

## 六、agent 相容性

同一套 proxy 應付多款 agent，差別只在「怎麼告訴它 base URL 換了」。

| Agent | 指向方式 | 編輯機制 | 狀態 |
|---|---|---|---|
| Aider | `OPENAI_API_BASE` | 純文字回覆（diff-edit） | **已實測通過** |
| OpenCode | `opencode.json` 自訂 provider（`@ai-sdk/openai-compatible`） | function calling | **已實測通過**（過程中挖出並修好還原機制的一個洞，見下） |
| Continue | `~/.continue/config.yaml` 自訂 `provider: openai` + `apiBase` | function calling | **已實測通過**（再次驗證 tool_calls 還原修復不是只對 OpenCode 有效） |
| Cline | GUI 設定選 **OpenAI Compatible**，填 Base URL/API Key/Model | function calling | **已實測通過**（第三款驗證同一個修復） |
| Codex | `config.toml` 自訂 provider（`wire_api = "responses"`） | **Responses API**（`POST /v1/responses`，欄位結構完全不同） | **已實測通過**（遮蔽與還原兩側原本都靜默失效，見下；**寫檔路徑 08-22 補驗完成**，見下方註記） |
| Claude Code | `ANTHROPIC_BASE_URL` | Anthropic Messages API（欄位結構完全不同，另有協定翻譯層） | **已實測通過**（純文字對話 + 工具呼叫，含真串流；圖片/文件附件尚未支援，見下） |
| **Cursor** | — | 廠商代管後端，無自訂位址欄位 | **不支援**（見上「BYOK vs. 代管帳號」） |

「編輯機制」這一欄是 OpenCode 測試後才加的——它正是還原邏輯要走哪條
程式碼路徑的決定因素（見下），後續驗證新 agent 時應該優先確認這一欄。

「需擴充」只涉及 `proxy/detector.py` 的 `extract_texts()` ——
不同協定把使用者內容放在 JSON 的不同位置。`main.py`、`forward.py`、
對照表**完全不需更動**；還原邏輯原本也以為不用動，直到 OpenCode 測出下面這個洞。

> 定位：**一個載體，配幾個小轉接頭**，不是六個載體。

### 🔴 OpenCode 實測挖出的洞：還原只認文字回覆，沒讀過工具呼叫

AI 讓 agent 知道「要怎麼改檔案」有兩種方式：**純文字回覆**
（`delta.content`，Aider 這類走 diff-edit 格式的工具用這條）、
**function calling**（`delta.tool_calls[].function.arguments`，OpenCode
這類用內建編輯工具的 agent 走這條）。`core/redact/restorer.py` 的
`SSERestorer` 一開始只處理了 `delta.content`——不是轉換邏輯寫錯，是這段
程式碼從來沒讀過 `tool_calls` 這個欄位。

實測用 OpenCode 叫它改一個含假身分證字號的檔案時，**磁碟上的檔案被寫入
了 `[TW_ID_1]` 這類佔位符，不是真值**。比「沒遮到」更糟——沒遮到只是那次
沒受保護，這個是把錯誤內容實際寫進使用者的檔案，跟第一版遮蔽不還原時
Aider 壞掉是同一類問題，只是這次是靜默發生，連錯誤訊息都沒有（log 只是
平淡地顯示「還原 0 筆」）。

**修法**：`SSERestorer` 新增處理 `tool_calls[].function.arguments`，用
`index` 幫每個工具呼叫維護獨立的 buffer（同一回覆可能同時有多個工具呼叫
在串流，例如一次改兩個檔案，共用一個 buffer 會把不同呼叫的內容拼錯）。
修復前用隔離測試（不打真實 API）先確認根因，修完後重跑真實 OpenCode
端到端：磁碟檔案完全乾淨，log 出現「還原 32 筆」。詳見 PR #11。

**這件事的啟示**：agent 相容性不能只看「能不能連上、送不送得出去」，
**編輯機制本身（純文字 vs. function calling）會影響還原這一側走的是哪條
程式碼路徑**。後續測 Continue / Cline / Codex / Claude Code 時，這是
優先要確認的事——它們是走文字回覆還是工具呼叫。

### Claude Code：多一層協定翻譯，而不是多一份遮蔽/還原邏輯

Claude Code 走的是 Anthropic Messages API（`POST /v1/messages`），跟其他
五款 agent 共用的 OpenAI 相容格式（`/v1/chat/completions`）完全不同——
不是欄位少幾個的問題，是端點、訊息結構、串流事件格式整個不一樣。而且
**AIR 上游根本不支援 Anthropic 格式**（實測直接回 404
`unsupported_endpoint`），所以這條路徑不能只做「挖文字」，還得整包
**協定轉換**：Anthropic 請求 → OpenAI 相容格式 → 真的送給 AIR → 換回來。

**決定：轉換層之外，遮蔽/還原完全沿用既有機制，不重寫一套。**

- Anthropic 的 `messages[].content`／`system` 文字 block 形狀
  （`{"type": "text", "text": "..."}`）跟 OpenAI 多模態 content parts
  重疊，`detector.extract_texts()` 稍微擴充（新增掃 `system` 欄位、
  `tool_use.input` 任意深度巢狀 JSON 裡的字串葉節點、`tool_result.content`）
  就能直接吃 Anthropic 格式的 payload，`masker.mask_payload()` 完全不用改
- 還原沿用 `restorer.restore_body()`（非串流）與 `restorer.SSERestorer`
  （串流），在 AIR 回覆的原始 JSON／SSE 位元組上做文字取代——這兩個都是
  對 OpenAI 格式寫的，但因為還原是在**序列化後的原始位元組**上做正則
  取代，跟外層是什麼協定無關，天然可以重用

新寫的只有 `proxy/anthropic_adapter.py` 這一個模組，純粹負責格式互轉：
`to_openai_request()`（Anthropic → OpenAI，含 `tool_use`/`tool_result`/
`tools[]` 的轉換）、`response_to_event_stream()`（非串流回覆包成 Anthropic
SSE，簡化版）、`AnthropicStreamTranslator`（真串流版，邊收 AIR 的 OpenAI
格式 delta 邊即時翻譯成 Anthropic 事件）。目前還不支援圖片／文件附件
（`image`/`document` block），遇到會回 501 誠實拒絕，不硬翻。

**為什麼 `tool_use.input` 一定要重新掃**：assistant 的 `tool_use` block
一旦被 proxy 還原、送回 Claude Code，裡面就是真值。Claude Code 每次請求
都重送整段對話歷史，下一輪這則歷史訊息會帶著真值再出現，若不重新遮蔽
就直接轉送給 AIR，真值等於外洩——跟上面 OpenCode 那個洞是同一類問題
（工具呼叫路徑容易被忽略），只是方向相反：那次是「還原沒做，佔位符
外洩給使用者」，這次若疏漏會是「真值外洩給雲端 AI」。已用真實請求
驗證過這條路徑正確運作。

**踩到一個只有真實環境才會浮現的坑**：官方 OpenAI 規格允許 assistant
訊息只有 `tool_calls`、沒有文字時 `content` 是 `null`，但 AIR 的驗證比
規格嚴格，會直接拒絕（400）。改成沒有文字時給空字串 `""`。這種「規格
允許但特定供應商不接受」的落差，光看規格文件或用 mock 測試量不出來——
mock 只會回你安排好的回覆，不會告訴你「你送出去的請求，上游願不願意
收」，這個 bug 是真的打 AIR 才浮現的，也是後續加新 agent／新上游時要
記得的教訓：協定翻譯層寫完一定要跑一次真實環境。

### Codex：不用翻譯協定，但兩側都靜默失效了

Codex CLI 走 **Responses API**（`POST /v1/responses`）。好消息是**上游 AIR
支援這個端點**（回 200），proxy 的萬用路由直接轉發就通，不像 Claude Code 那次
要寫一整層協定翻譯。壞消息是「連得上」跟「保護得到」是兩回事——**遮蔽與還原
兩側都對這個格式完全無效，而且沒有任何錯誤訊息**。

**請求側**：真實請求 47,497 字元，`extract_texts()` 抓到 **0 個欄位、0 字元**。

| 欄位 | 原本為什麼漏掉 |
|---|---|
| `instructions`（21,026 字元的系統提示） | 根本不在掃描範圍內 |
| `input[].content[].text`（對話訊息） | `input` 的處理是為 embeddings 寫的，只認字串／字串陣列；這裡是**物件陣列**，`isinstance(item, str)` 一律 False，整段靜默跳過 |
| `input[].arguments`（工具呼叫參數） | 同上 |
| `input[].output`（工具執行結果，**agent 讀到的檔案內容在這裡**） | 同上 |

**回覆側**：`SSERestorer` 只認 `choices[].delta.content`，而 Responses 的事件是
頂層 `{"type": "response.*", "delta": ...}`，**一筆都沒還原到**。其中
`response.function_call_arguments.delta` 是 agent 實際要寫進檔案的內容——漏掉
就是把佔位符寫進使用者的程式碼，跟 OpenCode 那次是同一個坑的不同外殼。另外
`response.completed` 這類事件帶的是完整最終結果，Codex 從那裡取結果，因此
只還原 `delta` 不夠，完整事件也要整包還原。

**三次踩到同一類坑，這次把判準寫下來**：OpenCode 是「還原 0 筆」、Claude Code
早期是「`tool_use.input` 沒重掃」、Codex 是「偵測 0 筆」。共同點是
**log 看起來完全正常**——「偵測到 0 筆」跟「這次剛好沒個資」在畫面上長得一樣。
所以新增 agent 支援時的驗收條件不是「proxy 沒報錯」，而是**拿真實 capture 確認
「抓到的字元數 > 0」，並且用一個「AI 答錯就代表它看到真值」的問題交叉驗證**
（實測反例：問「`A123456789` 有幾個字元」，答 10 就是看到真值，遮蔽後應該是
9 個字元的 `[TW_ID_1]`）。

#### 寫檔路徑：08-22 補驗完成（結論分兩半）

合併 PR #29 時，「agent 主動寫檔」那條路徑只有單元測試涵蓋。08-22 用真 Codex
（`gpt-4.1`、純規則層）補驗，**通過的部分**：

| 項目 | 證據 |
|---|---|
| 請求側從 `function_call_output` 挖出檔案內容並遮蔽 | 兩輪在 agent 讀檔後都印「已遮蔽：6 筆（`TW_ID` x3、`TW_PHONE_M` x3）」 |
| 回覆側 `function_call_arguments.delta` 還原 | 7 次還原事件 |
| **還原後的真值寫進磁碟、讀回來零佔位符** | 模型寫出 `temp_patch.diff`，`cat` 回來是 `return "A123456789"` |
| 效能 | 遮蔽 1.6〜5.8 ms；快取命中率 57% → 87%；對照表 6 個不重複值 |

**最硬的一條是閉環**：agent 把自己剛寫出的檔案讀回來時，規則層在裡面**又多抓到
一個 `TW_ID`**（16 筆 → 17 筆）。若還原失效、落到磁碟的是 `[TW_ID_1]`，偵測器
不可能多抓到這一筆 —— 佔位符不會被判成身分證。這比「log 說還原了 N 筆」更可信，
因為它是從**磁碟上實際的位元組**倒推回來的。

**沒通過的部分（誠實記錄）**：內容始終沒進到任務指定的那個檔案，該檔 sha256
從頭到尾與基準線相同。原因與 proxy 無關 —— 模型在 Windows 上拼不出合法的
PowerShell（`&&` 不是合法分隔符、`echo ... ()` 解析錯誤、`"""` 被當成參考運算子）。
**而且兩輪最後模型都回報「已成功新增」，兩次都是假的**（08-16 在 `gpt-4.1-mini`
上看到的現象重現）—— **agent 回報成功 ≠ 真的做了，一律以 sha256 為準。**

刻意**不跑第三次**：驗收條件的實質內容已達成，再跑只是賭模型會不會突然會用
PowerShell。為了讓檔名剛好對而重跑到成功為止，會讓報告出現一個看起來漂亮、
實際上是選擇性呈現的數字。

**Codex 同時具備兩種模式，強化了限制 2 的論述**：Codex 預設用 ChatGPT 帳號登入
（廠商代管後端，攔不到），只有自訂 provider（BYOK）模式才攔得下來。這比 Cursor
更有說服力——**同一個工具**、同一套程式碼，差別只在認證方式。這證明判準不是
「哪個廠牌的 agent」，而是「流量走不走得到你指定的位址」。

## 七、與其他成員的介面

### 對 A / D（偵測核心）

proxy 只透過 `proxy/detector.py` 呼叫 `core.rules.detect_all()`，
介面若變動只需改這一個檔案。

proxy 依賴的保證：

1. `text[start:end]` 等於該 span 的 `text` 欄位（字元索引）
2. `detect_all()` 回傳的 spans **互不重疊**（Layer 4 已保證）
3. `type` **應該**是大寫英文與底線組成（佔位符 `[TYPE_N]` 的格式依據）——
   但 proxy **不完全信任這件事**：語意層曾經原生輸出過小寫代碼，`mapping.
   normalize_type()` 在入口做防禦性正規化（見決定 9）。這條保證上游修好了
   （D 後來在 `core.ner.detector` 也轉大寫），但下游的防線沒有因此撤掉。

proxy **不依賴** `replacement` 的序號（見決定 3），也不依賴 `confidence`
做遮蔽與否的判斷（`confidence` 過濾在偵測層已經做完）。

語意層已接入（見決定 10）：proxy 呼叫 `detect_all(text, extra_spans=
detect_ner(text))`，由 `PII_ENABLE_NER` 控制是否啟用。

### 對 C（瀏覽器擴充）

兩個載體共用同一套遮蔽 / 還原邏輯，住在 **`core/redact/`**（issue #23，
已於此搬遷完成）。這個套件與 proxy 無耦合 —— 不認得 API 協定、
不讀環境變數，拿到的只是「一段文字加一組 span」：

| 模組 | 提供什麼 |
|---|---|
| `core.redact.mapping.MappingTable` | `token_for(type, value)` / `value_for(token)` / `restore_text(text)` |
| `core.redact.mask_text(text, spans, table)` | 單段文字的遮蔽 |
| `core.redact.restore_text(text, table)` | 單段文字的還原 |
| `core.redact.StreamRestorer` | 逐段抵達的文字（C 若有串流需求） |

**沒搬過去的是 payload 層**（`proxy/masker.py` 的 `mask_payload()`、
`proxy/detector.py`、`proxy/config.py`、`proxy/risk.py`）。分界線是
「認不認得 API 協定」：從 OpenAI／Anthropic 的 JSON 挖出該掃的欄位、
讀 proxy 的環境變數、印風險警示，都是載體專屬的事，搬進 `core/` 會讓
它反過來相依 `proxy/`。C 面對的是使用者貼上的一段文字，本來就用不到。

**一個要講準的地方**：`core/redact/` 是 Python，而擴充是獨立的
TypeScript 實作，**不會直接 import 這份程式碼**。它的角色是「唯一的
權威參考實作」—— 佔位符格式、發號規則、查不到時的行為以這裡為準，
不是各自從頭想。搬遷帶來的是「只有一份權威定義」，不是自動共用。

**提醒 C**：若直接使用 `detect_all()` 回傳的 `replacement` 作為佔位符，
會踩到決定 3 描述的跨請求號碼錯亂問題。
